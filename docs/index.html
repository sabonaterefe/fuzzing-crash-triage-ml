ML-Assisted Crash Triage for Coverage-Guided Fuzzing

Fuzzing the c-ares DNS library with AFL++ and AddressSanitizer, rediscovering a real, documented vulnerability (CVE-2017-1000381) from scratch, and triaging the resulting crashes with density-based clustering (HDBSCAN) instead of manually reading every stack trace by hand.

01 Overview

Most small fuzzing projects stop at "the fuzzer found some crashes." The harder, more realistic problem — the one security teams actually deal with at scale — is triage: given a pile of crashing inputs, which ones are actually the same bug, and which are genuinely distinct issues worth separate attention?

This project builds that triage pipeline end to end, on a real target with a real, documented vulnerability as ground truth:

  1. Fuzz c-ares (the DNS resolution library used by Node.js and curl) at a version that predates a known CVE fix.
  2. Collect crashes with AFL++ + AddressSanitizer over a multi-day campaign.
  3. Extract and symbolize stack traces for every crash.
  4. Compare three triage approaches of increasing sophistication: naive raw-output deduplication, frame-signature matching (the approach real crash-reporting systems like Mozilla Socorro use), and HDBSCAN clustering over vectorized stack frames.
  5. Root-cause the findings against the actual upstream CVE patch, and verify the fix resolves every crash.

The target vulnerability is CVE-2017-1000381: an out-of-bounds read in ares_parse_naptr_reply(), fixed in c-ares 1.13.0. This project fuzzes c-ares 1.12.0 (the version immediately before the fix) and rediscovers the bug independently through fuzzing, without looking at the patch first.

02 Methodology

Target & harness

c-ares 1.12.0 was built with afl-clang-fast and AddressSanitizer (-fsanitize=address -g -O1 -fno-omit-frame-pointer). A minimal harness reads a file, feeds its raw bytes into ares_parse_naptr_reply(), and frees the result — isolating exactly the code path under test.

Seed inputs weren't hand-rolled byte arrays. Instead, two valid NAPTR DNS responses were generated using c-ares's own test infrastructure (test/dns-proto.h/.cc), so the fuzzer starts from real, well-formed wire format rather than guessing the DNS packet structure from nothing.

Fuzzing

AFL++ ran in persistent coverage-guided mode (afl-fuzz) against the instrumented binary, with ASAN_OPTIONS=abort_on_error=1 so AFL++ correctly recognizes ASan-reported memory errors as crashes rather than silent hangs.

Crash triage methods compared

MethodApproach
Naive dedup Exact match on raw ASan output. Represents "no triage logic at all."
Frame-signature matching Dedup on the top-N stack frame function names, ignoring addresses/line numbers — the real technique used by crash-reporting systems like Mozilla Socorro.
HDBSCAN TF-IDF vectorization of each crash's full frame sequence (function + file + line), clustered with density-based HDBSCAN.

HDBSCAN was chosen over k-means deliberately: the number of distinct bugs in a crash set is unknown ahead of time. K-means forces a predetermined k; HDBSCAN infers cluster count from density and can explicitly label sparse, one-off crashes as noise rather than force-fitting them into a bad cluster.

04 Crash Triage Comparison

All three methods were run on the same final set of 16 unique crashes (deduplicated by content hash). The results make the case for each method's practical value:

Naive dedup
16 groups — fails completely
Frame-signature
1 group
HDBSCAN
2 groups

Naive dedup fails outright: it reports all 16 crashes as unique, because AddressSanitizer embeds live memory addresses (heap pointer, program counter, stack/base pointer) in every report. Even identical bugs never produce byte-identical output twice. This is what "no real triage" looks like in practice.

Frame-signature matching correctly collapses all 16 crashes into a single group, since it ignores addresses and line numbers, using only the top stack frames' function names.

HDBSCAN finds more real structure: it splits the same 16 crashes into two clean clusters with zero noise points, because it uses the full frame information including exact line numbers. This split isn't an artifact — it corresponds to two genuinely distinct trigger points within the same vulnerable function, confirmed in the root-cause analysis below.

Cluster 0 — 3 crashes

All crash at ares_parse_naptr_reply.c:137 — the order field read

Cluster 1 — 13 crashes

All crash at ares_parse_naptr_reply.c:139 — the preference field read

This result held consistently at every checkpoint as the campaign ran longer (re-verified at 5, 9, 13, and 16 crashes) — it's a reproducible finding, not a small-sample coincidence.

05 Root Cause

Both crash sites are in the same few lines of ares_parse_naptr_reply.c, reading two fixed 16-bit fields with no check that the buffer actually has enough bytes left: 

vptr = aptr;
naptr_curr->order = DNS__16BIT(vptr);        line 137
vptr += sizeof(unsigned short);
naptr_curr->preference = DNS__16BIT(vptr);   line 139
vptr += sizeof(unsigned short);

If the record's remaining data is shorter than expected, reading order (line 137) or the next two bytes for preference (line 139) walks past the end of the heap-allocated response buffer — confirmed by AddressSanitizer as a 1-byte heap-buffer-overflow READ immediately past the allocated region in every captured crash.

This matches the real, documented CVE-2017-1000381 advisory exactly. The official fix (c-ares 1.13.0) adds a single bounds check before this block: 
@@ -111,6 +111,13 @@ ares_parse_naptr_reply (const unsigned char *abuf, int alen,
           status = ARES_EBADRESP;
           break;
         }

+      /* RR must contain at least 7 bytes = 2 x int16 + 3 x name */
+      if (rr_len < 7)
+        {
+          status = ARES_EBADRESP;
+          break;
+        }
+
       /* Check if we are really looking at a NAPTR record */
       if (rr_class == C_IN && rr_type == T_NAPTR)
7 bytes covers the two 16-bit fields plus the minimum 1-byte length prefix for each of the three string fields that follow. One check upstream of both reads eliminates both crash sites at once — which is exactly why HDBSCAN's two clusters are "the same root cause, two trigger points," not two unrelated bugs.

Sources: c-ares official security advisory, Red Hat Bugzilla CVE-2017-1000381.

06 Fix & Verification

The real upstream patch was applied to a separate, patched build of c-ares (leaving the original vulnerable build untouched for the live campaign), and every saved crash input was re-run against it as a regression test.

0

Every single crash input that previously triggered an ASan heap-buffer-overflow exits cleanly (exit code 0, no ASan report) against the patched build. This confirms the bug found by fuzzing is the actual documented vulnerability, verified with the real fix rather than a guessed one.

07 Limitations & Honest Notes

  • The campaign ran on a personal laptop (WSL2 on Windows 11), not a dedicated fuzzing server. It was interrupted several times by WSL restarts (most likely triggered by Windows updates or the host sleeping for extended periods) and had to be resumed with AFL++'s AFL_AUTORESUME mechanism each time. No crash data was lost across these interruptions, but cumulative wall-clock time includes idle/suspended periods, not pure continuous execution.
  • All 16 discovered crashes reduce to one underlying vulnerability class (a missing bounds check hit at two adjacent lines). A longer campaign, a richer seed corpus, or fuzzing additional parsing functions in c-ares would likely surface more diverse bug classes, which would make the clustering comparison even more interesting to study.
  • HDBSCAN's TF-IDF-over-frame-text representation is simple by design, to keep the method transparent and explainable. A production triage system would likely combine this with additional signal (crash type, fuzzer-provided minimization, binary diffing) rather than relying on stack traces alone.
